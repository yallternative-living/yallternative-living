## 1. What the code actually does

**`sw.js`** (full file read, 197 lines)
- `CACHE_NAME` (`sw.js:8`) is a content-derived hash: `yallternative-cache-vb4164e587607`, written by `scripts/build-site-data.js`'s `updateServiceWorker()` (`scripts/build-site-data.js:2828-2884`). It's a `sha256` over the precache list's entry names *and* file contents (`:2861-2871`), truncated to 12 hex chars — deterministic, changes only when a precached file or the list itself changes. Good: fixes the old wall-clock-timestamp scheme (H-20, referenced in the comment at `:2828-2833`) that renamed the cache, and blew away every visitor's cache, on every deploy regardless of content.
- `ASSETS_TO_CACHE` (`sw.js:11-54`) precaches 36 entries: 16 HTML pages (including `/`, `/thank-you.html`, `/order-status.html`, `/404.html`), both CSS files, 13 JS files (`main.js`, `cart.js`, `thank-you.js`, all `*-data.js` including `products-data.js`), manifest, favicons, logo. `journal.html` is conditionally spliced in by the build script (`:2836-2845`) based on a CMS toggle.
- `install` (`sw.js:62-72`): `cache.addAll(ASSETS_TO_CACHE)` then `self.skipWaiting()` — unconditional, no user gate.
- `activate` (`sw.js:80-106`): enables navigation preload (feature-detected, safe no-op on iOS Safari per the code comment at `:87`), deletes every cache whose name isn't the current `CACHE_NAME`, then `self.clients.claim()`.
- `fetch` (`sw.js:115-197`):
  - Non-GET: ignored (`:116`).
  - `/.netlify/*` and `/api/*`: returns before any cache logic at all (`:128-130`) — this is the C-3 fix (see below).
  - Same-origin requests: query string is stripped for the cache key (`:134-135`).
  - Navigations and `.js`/`.css` (`isNavigation || isCodeAsset`, `:138-142`): **network-first**. Awaits `event.preloadResponse` for navigations, else `fetch()`; on success, clones into the SW cache; on failure, falls back to `caches.match(cleanRequest)`, and for navigations specifically, falls back further to the cached `/index.html` shell (`:166`) — not a dedicated offline page.
  - Everything else (images, fonts, JSON data files, etc.): **stale-while-revalidate** (`:170-195`) — serve cache immediately if present, always fire a background `fetch()` to refresh the cache.
  - Note: the `fetch()` calls in both branches use the default `Request` cache mode (no `cache: "reload"` anywhere in this file), so they are themselves subject to the browser's ordinary HTTP cache — see §3.

**Registration — `assets/js/main.js:5304-5377`**
- Gated on `"serviceWorker" in navigator` (`:5304`).
- `controllerchange` listener (`:5317-5361`) shows a toast ("A new version is available!" with Update-now / dismiss buttons) — but only on a genuine hand-off away from an *existing* controller. A `hadController` flag (`:5316`) suppresses the toast on first install, because `skipWaiting()` + `clients.claim()` also fire `controllerchange` for a brand-new visitor (comment at `:5309-5315` explains this explicitly — it's a deliberate, documented fix for a prior false-positive-toast bug).

**Build-time cache-name bump — `scripts/build-site-data.js:2828-2884`** (see above). This runs *after* all HTML injection/cleanup passes (`:2824-2825` comment), so the digest reflects final shipped bytes.

## 2. Web research (primary sources, dated)

1. **Precaching vs. runtime caching** — Chrome for Developers / Workbox docs: precache the minimal app shell; treat large/variable/infrequently-used resources as runtime-cached, not precached, because precaching everything inflates install time and cache storage and "may be an anti-pattern." https://developer.chrome.com/docs/workbox/caching-resources-during-runtime/ (Chrome for Developers, retrieved 2026-09)

2. **Service worker lifecycle, `skipWaiting`/`clients.claim`** — web.dev: `skipWaiting()` makes the new worker activate immediately, but it is very likely now controlling clients that were loaded under the *old* worker/old cached assets — a live page can end up with old HTML fetching from a SW that expects a different asset shape. web.dev explicitly warns to plan around this rather than use it blindly. https://web.dev/articles/service-worker-lifecycle (web.dev, retrieved 2026-09); `clients.claim()` semantics: MDN https://developer.mozilla.org/en-US/docs/Web/API/Clients/claim (retrieved 2026-09).

3. **Navigation preload** — web.dev: SW boot-up cost is ~50ms desktop / ~250ms mobile before it can even start a navigation fetch; `navigationPreload.enable()` starts that fetch in parallel. Pure win for a network-first HTML strategy, exactly the pattern `sw.js:88-94,151` implements. https://web.dev/blog/navigation-preload (web.dev, retrieved 2026-09)

4. **Offline fallback page pattern** — web.dev: intercept failed navigations and serve a dedicated, minimally-styled offline page rather than the browser's default error page or a stale cached page. https://web.dev/articles/offline-fallback-page and https://web.dev/articles/offline-cookbook (web.dev, retrieved 2026-09). This repo's `sw.js:166` instead falls back to cached `/index.html` for any failed navigation — not a dedicated fallback, and not necessarily accurate (a shopper offline mid-checkout is shown the homepage, not a "you're offline" state).

5. **HTTP caching / `must-revalidate`, `stale-while-revalidate` interaction** — RFC 9111 §4.2.4: `must-revalidate` forbids serving a stale response without successful revalidation, full stop, even when disconnected (a cache "MUST generate an error response rather than reuse the stale response"). https://www.rfc-editor.org/rfc/rfc9111.html (IETF, June 2022). Cloudflare's docs on the RFC 5861 `stale-while-revalidate` directive note it is *disabled* by the presence of `must-revalidate`/`no-cache`/`s-maxage`. https://developers.cloudflare.com/cache/concepts/revalidation/ (Cloudflare Docs, retrieved 2026-09).

6. **Netlify's actual default HTML behavior** — Netlify forces `Cache-Control: public, max-age=0, must-revalidate` on HTML regardless of what you configure, paired with an ETag so the edge can answer with 304s cheaply. Netlify Support Forums, corroborated across multiple threads: https://answers.netlify.com/t/is-cache-control-public-max-age-0-must-revalidate-supposed-to-be-the-default/55403 and https://answers.netlify.com/t/netlifys-default-cache-headers/11992 (retrieved 2026-09); official overview: https://docs.netlify.com/build/caching/caching-overview/. This matches and confirms the `netlify.toml` comment.

7. **Netlify static-asset caching** — Netlify's own CDN treats static assets as fresh for up to a year and auto-invalidates on new deploys at the *edge*; that's independent of what the *browser* does with the `Cache-Control` header Netlify sends downstream (7 days here for CSS/JS). https://docs.netlify.com/build/caching/caching-overview/ (Netlify Docs, retrieved 2026-09).

8. **`fetch()` `cache` modes** — MDN: `reload` bypasses the browser HTTP cache for the request but still writes the result back into it; default mode consults the HTTP cache using normal freshness rules first. https://developer.mozilla.org/en-US/docs/Web/API/Request/cache (MDN, retrieved 2026-09). `sw.js` never sets `cache: "reload"` on any `fetch()` call (`:153`, `:175`) — see §3.

9. **iOS Safari storage** — WebKit's own blog: Cache API storage quota is a fixed 50 MiB per origin/partition on iOS/iPadOS; once hit, the page must evict its own entries. A 7-day cap on script-writable storage applies to Safari tabs (resets on any Safari use within the window; does **not** apply once the site is added to the home screen with `display: standalone`). https://webkit.org/blog/14403/updates-to-storage-policy/ (WebKit Blog, retrieved 2026-09); background: https://adactio.com/journal/16619 ("Apple's attack on service workers", Jeremy Keith, referencing the original policy).

10. **bfcache and service workers** — Chrome for Developers: a page is evicted from bfcache if, while cached, its controlling SW is claimed, receives a message, activates a new version, or is unregistered. A same-origin SW that is *already* controlling the page and does nothing mid-bfcache is fine; it's SW *lifecycle events firing while a page sits in bfcache* that evict it. https://developer.chrome.com/blog/back-forward-cache/ and the bfcache blocking-reasons reference at https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/Monitoring_bfcache_blocking_reasons (retrieved 2026-09). Relevant here: `clients.claim()` on every activation (`sw.js:103`) is exactly the kind of event that can evict any tab of this same site sitting in another tab's bfcache at deploy-update time — a real, if narrow, interaction with the current design.

11. **PWA/e-commerce guidance, 2026** — Chrome for Developers: since ~2022, an install prompt no longer requires a service worker at all — manifest + HTTPS is sufficient; a SW is only needed for offline support, background sync, or push. https://javascript.ac/en/blog/service-workers-pwa-guide (secondary summary of Chrome's own installability criteria, retrieved 2026-09) and Web Almanac 2025 PWA chapter noting full PWA adoption is still ~3.5% of mobile sites: https://almanac.httparchive.org/en/2025/pwa (HTTP Archive, 2025).

## 3. Netlify CDN vs. browser HTTP cache vs. SW cache — the actual interaction on THIS site

This is the sharpest finding, worth stating precisely because the three layers don't line up:

- **Netlify's edge** invalidates on every deploy automatically (per Netlify Docs, item 7 above) — the CDN itself is never the stale layer.
- **The browser's HTTP cache** obeys the `Cache-Control` header Netlify sends downstream: `public, max-age=604800` for `/assets/css/*` and `/assets/js/*` (`netlify.toml`). Because these assets are requested at a **static** URL — `assets/css/styles.css?v=2.0`, `assets/js/main.js?v=2.0` (`index.html:45,515`) — a CSS or JS edit that ships in a new deploy does **not** change the request URL. A returning visitor's browser can serve the *old* file straight out of HTTP cache for up to 7 days without even asking Netlify, deploy or no deploy.
- **The service worker's own cache** (`CACHE_NAME`) *does* roll on any precached-file change (§1), so in isolation the SW is doing the right thing — but its `fetch()` calls for the network-first code-asset path (`sw.js:153`, no `cache: "reload"`) go through the *same* browser HTTP cache. Concretely: SW intercepts a request for `main.js`, calls `fetch(event.request)` with default cache mode → browser HTTP cache has an unexpired (≤7 day) entry from before the deploy → the "network" fetch silently returns the stale bytes → SW writes those stale bytes into its own (correctly-named) cache anyway. The digest-based `CACHE_NAME` rotation is defeated by the very fetch it uses to populate the new cache. Net effect: a shopper who visited within the last 7 days can be served **stale CSS/JS for up to 7 more days after a price, layout, or bug-fix deploy**, even though the SW "updated."
- `cache: "reload"` on that one `fetch()` call would fix it (bypasses HTTP cache, still writes the fresh response into both HTTP cache and SW cache) — MDN item 8 above. Versioned/hashed URLs (`main.js?v=<content-hash>` or `main.<hash>.js`) would fix it more robustly and is the standard fix (item 1, 6); the `?v=2.0` scheme here is not that — it hasn't been bumped to track deploys (confirmed static across current `index.html`), so it currently provides zero cache-busting benefit despite looking like a version marker.
- **HTML** is unaffected by this specific problem: Netlify forces `must-revalidate` on HTML regardless of config (item 6), so the browser always round-trips to check freshness, and the SW's own network-first-for-navigations path plus navigation preload (`sw.js:138-151`) is layered on top of that already-fresh channel. HTML staleness on this site is bounded by the SW's cache fallback only (used when the network request itself fails), not by HTTP caching.

## 4. Answers

### Q1 — Does precache-everything help or hurt a store whose prices/stock/cart/pages change every deploy?

**Net: this SW is closer to right than wrong, but "precache everything" is doing the store no favors and creates one live hazard.**

- **Stale HTML risk**: low in practice. HTML is network-first (`sw.js:142-169`) with navigation preload, so a shopper online gets live HTML on every navigation; the precached copy is a fallback used only on network failure or first offline visit. The genuine exposure is narrower than "precaching HTML is dangerous" — it's that the *fallback-of-a-fallback* is always `/index.html` (`:166`), not the page the shopper actually asked for and not a dedicated offline page. A shopper who goes offline mid-navigation to, say, `/shop.html` after their cache entry for it expired or was evicted gets bounced to the homepage.
- **Update lifecycle**: `skipWaiting()` + `clients.claim()` unconditionally (`:70`, `:103`) means a new SW takes control of *already-open* tabs immediately, without asking. Per web.dev (item 2), the standard risk is old-page-JS-talking-to-new-SW-expectations; this codebase mitigates the worst version of that by keeping the fetch handler's request/response shape stable across versions and by not auto-reloading (the toast requires a click, `main.js:5339`). But note precisely what "controlling" means here: the *already-loaded* JS/HTML in the tab doesn't change until the shopper reloads — only *new* fetches from that tab (images, further nav) are now handled by the new SW/cache. This is fine for this app's shape (no complex versioned client-server protocol), but it's relying on that being true, not enforcing it.
- **Digest cache name + toast for a returning shopper mid-session**: this is well done. The hash-based `CACHE_NAME` (§1) means a no-op rebuild is genuinely a no-op (no needless churn), and a real change rotates the cache exactly once — avoiding both "never updates" and "wipes cache every deploy" failure modes the comment (`build-site-data.js:2828-2833`) explicitly says it replaced. The toast correctly distinguishes first-install from a real update via the `hadController` flag (`main.js:5316-5321`) — a legitimately subtle bug (every fresh visitor being told "a new version is available" about the version they just loaded) that's been fixed with a comment explaining why.
- **"Two versions of `main.js` and `products-data.js` in memory" hazard**: real, and structurally unavoidable with `skipWaiting`. Because `clients.claim()` fires without a reload, an open tab can have `main.js` v1's closures still running in memory while any *new* fetch that tab makes (e.g., an XHR-like fetch for `products-data.js`, or a second script tag inserted at runtime) is served v2's data by the now-controlling new SW. For this codebase specifically, `products-data.js` is loaded once at initial page parse via a `<script>` tag, not re-fetched by JS at runtime, so the practical exposure is smaller than it sounds — the live tab keeps its original `products-data.js` for its whole session. The real hazard is the *next* same-tab navigation (e.g., clicking from shop.html to a product page) picking up new HTML paired with whatever JS bundle is cached, which is exactly what network-first-for-navigations is designed to avoid by fetching fresh HTML every time. Net: the mitigations already in place (network-first HTML/JS/CSS, no auto-reload) substantially defang this hazard; it isn't fully eliminated because nothing forces the tab to reload after claim.
- **Is network-first-for-HTML / SWR-for-assets / navigation-preload the safer 2026 default?** Yes — and the current `sw.js` already implements exactly that split (network-first for HTML+JS+CSS, SWR for images/fonts/data, navigation preload enabled). This matches Workbox's stated defaults (item 1) and web.dev's navigation-preload guidance (item 3). The design is sound; the execution has the one HTTP-cache interaction bug in §3 and the missing-offline-fallback-page gap in §5.

### Q3 — Netlify CDN vs. `Cache-Control: public, max-age=604800` on non-hashed assets

Covered in depth in §3 above. Summary: **`cache: "reload"` on the SW's code-asset `fetch()` call, or moving to content-hashed URLs, both independently solve it; the current code does neither.** Netlify's edge-level auto-invalidation-on-deploy (item 7) means the *CDN* always has the fresh file — the staleness is purely browser-HTTP-cache-in-front-of-a-static-URL, compounded by the SW's own "network" fetch trusting that same browser cache. Versioned/hashed filenames are the standard, more robust fix because they also solve it for *any* consumer of the URL (direct link-clicks, `<link>` prefetches, etc.), not just SW-mediated fetches; `cache:"reload"` is a narrower one-line fix scoped to the SW path only.

### Q4 — Keep a SW at all?

Keep it, with fixes. Reasoning against the 2026 landscape (item 11):
- The site doesn't need a SW for installability (manifest + HTTPS suffice since ~2022) — but that's not why this SW exists; it exists for the offline/repeat-visit story, which is a legitimate, separate justification.
- E-commerce-specific PWA data (item 11, Shopify/Web Almanac) points to real conversion/engagement upside from PWA patterns generally, but the *measured* benefit is overwhelmingly about installability, push, and app-like navigation — not precache-driven LCP wins over a well-configured HTTP cache. For a small static site already getting `immutable, 1y` on images and Netlify's edge CDN on everything else, the *incremental* repeat-visit LCP benefit of SW precaching specifically is modest; most of the win is already captured by HTTP caching, and this review found no first-party performance measurement in the repo (no RUM/LCP data comparing with-SW vs without) to justify a stronger claim either way.
- bfcache (item 10): `clients.claim()` firing on every activation is a documented bfcache-eviction trigger for *other* tabs of the same origin sitting in back/forward cache at that moment. Low-frequency event (only at deploy-driven SW updates, not every navigation), but it's a real, uncounted cost of the `skipWaiting`+`claim` combo that a network-first-with-HTTP-caching-only approach wouldn't have.
- Verdict: the offline/flaky-network story (rural/mobile shoppers, the site's likely audience given "alternative living" positioning) is a real and defensible reason to keep a SW; the implementation just needs the fixes in §5, not a rewrite or removal.

### Q5 — Concrete recommendation for this `sw.js`

**Keep and fix, don't remove or replace wholesale.** The architecture (network-first HTML/JS/CSS with navigation preload, SWR for the rest, hard bypass for `/api/` and `/.netlify/`, content-hash cache naming) is already 2026-appropriate. Four concrete fixes, ordered by impact:

1. **Add `cache: "reload"` to the network-first `fetch()` at `sw.js:153`** (and consider it for the SWR background-refresh `fetch()` at `sw.js:175` too, though that one's staleness window is bounded by SWR's own re-fetch-on-every-request behavior, so it's lower priority). Fixes the §3 interaction where a 7-day browser HTTP cache entry silently defeats the digest-based SW cache rotation for CSS/JS.
2. **Trim the HTML precache list** (`sw.js:12-26`) to the app shell — home, shop, 404, maybe one or two more — and let the rest (`terms.html`, `privacy.html`, `reviews.html`, `faq.html`, etc.) populate into the cache via the existing network-first runtime path on first visit. Reduces install-time work and precache storage without losing offline support for pages a shopper has actually visited.
3. **Add a dedicated offline fallback page**, precached, and change the final fallback at `sw.js:166` from `caches.match('/index.html')` to `caches.match('/offline.html')` when there's no cached copy of the requested page specifically.
4. **Comment (or split) the `isCodeAsset` check at `sw.js:140`** to make explicit that it intentionally also covers the `*-data.js` payloads (not just executable code) and why that's correct (freshness over speed for data) — currently reads as if it's meant for JS/CSS only and the data-file inclusion looks accidental to a future reader.

**Registration / update UX**: current design (silent `skipWaiting`+`claim`, toast-not-forced-reload) is a reasonable, already-documented choice (`main.js:5305-5308` comment explains the deliberate avoidance of force-reload to protect in-flight form state). No change recommended there. One gap: there's no visible handling of `updatefound`/`installing` state to tell the shopper an update is *downloading* — only the after-the-fact `controllerchange` toast — but that's a UX-polish nice-to-have, not a correctness issue.

**Test plan / what changes**:
- `scripts/qa-check.js:1540-1569` asserts every entry in `ASSETS_TO_CACHE` exists on disk (`sw.js: all N cached assets exist on disk`) and (`:2347-2351`) that `search-data.js` specifically is present in the list. Trimming the HTML list (fix #2) requires updating this second hard-coded-path assertion pattern if any currently-asserted-present file is removed — check for similar hard-coded "includes X" assertions for any HTML page being dropped from precache (a grep for `.includes(` near the `swSrc` variable at `qa-check.js:2347` is the place to look before trimming).
- Adding `cache: "reload"` (fix #1) needs a new automated check or at minimum a manual verification: deploy a CSS change, load the site with a warm 7-day-old HTTP cache (or DevTools "Update on reload" off + throttled), confirm the new CSS is picked up within one SW-cache-rotation without a hard refresh. No existing test in `scripts/worker-checkout.test.js` or `qa-check.js` covers SW fetch-mode behavior — this would be new coverage, likely a browser-integration test (the repo already separates `*.browser.test.js` per the audit's H-17 remediation) rather than the static `qa-check.js` script, since it requires simulating actual browser HTTP cache state.
- Adding an offline fallback page (fix #3) needs: (a) the new file added to `ASSETS_TO_CACHE` so `qa-check.js`'s existence check covers it automatically, (b) a test that a failed navigation with no cached copy of the target page returns the offline page, not the homepage — again likely a browser-integration test given it requires simulating a network failure mid-navigation.
