# Impact analysis: reversing the products/*.html doorway-page decision

Scope: read-only analysis of `/Users/steven/Documents/GitHub/yallternative-living`. No files modified. One local `python3 -m http.server` was started on port 8099 (not 8082/8090) purely to empirically test redirect behavior in the Claude Browser pane, then killed; nothing in the repo changed.

This is the current, deliberate architecture (audit finding **H-15**, `docs/AUDIT-2026-09-01.md:54,205`; `PROJECT.md:45-57`): the 19 `products/*.html` pages are "doorway" pages — `noindex, follow`, canonical to `shop.html`, no JSON-LD, absent from `sitemap.xml`, and they redirect to `shop.html#<id>` via a synchronous inline `<script>` in `<head>`. All Product/Offer/BreadcrumbList structured data instead lives in one `ItemList` block on `shop.html`.

## 3. How the site links into products/*.html today, and whether "recently viewed" ever fires for a real visitor

- **`shop.html` product cards never link to `products/*.html`.** The card renderer (`main.js:2971-3037`) emits an `<article class="card reveal" data-id="...">` with no `<a href>` around the product photo/title — clicking a multi-image card's active slide opens the JS-built `.lightbox-modal` via a `role="button"` div (`main.js:1040-1059`, `1805-1821`), not a navigation. There is no `<a href="products/...">` anywhere in `shop.html`'s output for a card.
- **Global search results DO link to `products/*.html`, not `shop.html#id`.** `assets/js/search-data.js` carries both a `"url": "products/<id>.html"` and a `"shopUrl": "shop.html#<id>"` field per product (e.g. `search-data.js:297-298` for sleep-salve). But `main.js:7137` builds the result `<a href>` from `attrEsc(safeLinkUrl(prod.url))` — i.e. it uses `url`, the doorway page. **`shopUrl` is generated (`build-site-data.js:1056,1085`) but never read anywhere in `main.js` or any other JS file** (`grep -rn "shopUrl" assets/js scripts` matches only its own definitions) — dead data. Today, clicking a search result sends a real visitor through the doorway-page redirect before landing on `shop.html#id`.
- **`generateProductJsonLd`'s dead `url`/`generateProductBreadcrumbJsonLd`'s dead final crumb both already point at `products/<id>.html`** (§1) — consistent with `search-data.js`'s `url` field, inconsistent with the *live* shop ItemList's `shop.html#id`. The two live systems (search, shop ItemList) already disagree today about the product's canonical address; a reversal would resolve that inconsistency in favor of `products/*.html`, which is actually the *majority* position among the code that references a "product URL" at all.
- **The "Complete the Ritual" section links PDP → PDP** (`products/sleep-salve.html:169,181`: `<a href="lavender-soak.html">`, `<a href="shea-butter.html">`). Because these pages are `noindex, follow` (not `nofollow`), a crawler landing on one PDP (e.g. via search-data's link, or a direct/social share) can discover and crawl every other PDP through these ritual cross-links even though none of them are in `sitemap.xml` and none are linked from `shop.html` itself.
- **Recently Viewed does not populate for a real human visitor today — empirically confirmed in this session.** `initRecentlyViewed()` (`main.js:8100-8144`) only calls `recordRecentlyViewed()` when `document.body` has class `pdp-page` or `.pdp-layout` exists (`main.js:8105-8107`), and it's invoked from a `defer`red `<script src="main.js">` at the very end of `<body>` (`products/sleep-salve.html:252`). The redirect script is a synchronous inline `<script>` in `<head>` (`products/sleep-salve.html:35`) that fires as soon as the parser reaches it — before any deferred script runs. Verified directly: served the live repo over a local static server, navigated a real browser tab to `products/sleep-salve.html`, and immediately after settling, `location.href` was `http://localhost:8099/shop.html#sleep-salve` and `localStorage.getItem('yl-recently-viewed')` was `null`. So for a real visitor, `recordRecentlyViewed` never runs, the "recently viewed" feature never gets a single entry from a PDP visit, and (per §2) there's no `#pdpRecentlyViewedSection` markup to render into even if it did. The only way `yl-recently-viewed` could ever be populated today is if some other page called `recordRecentlyViewed()` directly (grep shows the only 2 call sites are both inside `initRecentlyViewed`'s PDP branch) — so in the current architecture this whole feature (`localStorage["yl-recently-viewed"]`, `#recently-viewed-section` on `shop.html`, PROJECT.md's M3 contract) is effectively **inert** for every real visitor, doorway or no.

## 4. Image pipeline and static `<picture>` emission

- `assets/js/image-manifest.js` is a generated `window.YL_IMAGES` object keyed by the *original* image path (e.g. `"assets/img/backroad-soak-alt1.jpg"`), each entry: `{ key, width, height, size, variants: { avif: [{width,file}, ...], webp: [{width,file}, ...] } }` (`image-manifest.js:7-40`). Produced by `scripts/optimize-images.js` (not read in depth here).
- `scripts/build-site-data.js:1760-1900` (`injectPageCopy`, inside the main build closure) already implements exactly the mechanism needed: it re-parses `image-manifest.js` at build time into a local `MANIFEST` object (`1762-1791`, has to re-quote bare object keys since the file isn't valid JSON — `1779`), then for any CMS-authored hero/feature/bio/secondary/gift-card image marker that's wrapped in an existing `<picture>` element in the source HTML, it looks up `MANIFEST[imgPath]` and emits `<source type="image/avif" srcset="...">` + `<source type="image/webp" srcset="...">` + the original `<img>` as fallback (`1859-1899`), each `<source>`'s `srcset` built from `variants.avif`/`variants.webp` widths. This is what index/about/contact's hero images already ship with.
- **`renderProductPdpHtml` does not use this mechanism at all.** Its gallery image is emitted as a bare `<img src="../assets/img/<file>.jpg" ...>` (`build-site-data.js:3737-3743`) — no `<picture>`, no AVIF/WebP `<source>`, and only ever the single `product.image` (never `product.images[]`, which exists in the catalogue and is used for the shop card's multi-slide gallery).
- **Feasibility for a real PDP gallery**: the `MANIFEST` variable is declared inside the same top-level build closure that later calls `generateProductOgPages()` (a nested IIFE at `2785-2797`, closes over `MANIFEST` by scope), so wiring responsive `<picture>` markup into the PDP gallery from *inside that closure* is straightforward. The obstacle is that `renderProductPdpHtml` itself is a **separate, top-level function** (`3568`) with no access to that closure's `MANIFEST` — it would need `MANIFEST` (or a small `renderPictureHtml(imagePath, manifestEntry, opts)` helper factored out of lines 1859-1899) passed in as a parameter, alongside `product.images[]`, to emit a real multi-slide `<picture>`-based gallery with dots, matching what the shop card already does client-side via `cardGalleryHTML()`.

## 5. Risk register for the reversal

1. **Split ranking signals / duplicate structured data.** If both `shop.html`'s `ItemList` *and* a reinstated per-PDP `Product` JSON-LD advertise the same SKU with potentially different canonical URLs, that's exactly the "doorway + duplicate" pattern H-15 was written to kill. Decision needed: keep `shop.html`'s `ItemList` as a lightweight `ItemList` of `url`s only (no embedded `Offer`), and move the priced `Product`/`Offer`/`BreadcrumbList` payload fully onto each PDP (this is what `generateProductJsonLd`/`generateProductBreadcrumbJsonLd` are already built for); or keep both but make every `url` field agree (`products/<id>.html` everywhere, including the shop ItemList's `offers.url`/`item.url`, currently `shop.html#<id>` at `build-site-data.js:1378,1398`).
2. **Duplicate visible copy, not just schema.** The ~300-char product blurb (`product.description`/`blurb`) is the only body copy that exists per product; it already appears in both `shop.html`'s card/quick-view *and* the PDP (`pdp-blurb`, `itemprop="description"`). Making the PDP the indexed page without adding PDP-unique long-form copy risks Google treating shop.html and the PDP as near-duplicate content once both are indexable — currently moot because only one of the two is indexed.
3. **CSP hash churn.** Deleting the redirect script removes the one PDP-wide inline-script hash (`sha256-VJ7jNsHEHhcsOXcbS3AonhQ32XVieLA091IRBqiUMZQ=` in `scripts/inline-script-hashes.json`), which `build-security-headers.js` will report as stale (non-fatal) unless removed in the same commit. If the reversed template adds any *new* inline script (e.g. the no-flash theme-init snippet the other 15 pages carry, needed once PDP gets a real `.theme-toggle`), that's a brand-new hash that must be reviewed and added to the baseline or the build fails (`build-security-headers.js:280-301`).
4. **Tests to rewrite are wide, not just the doorway assertions.** Direct hits: `verify-pdp-metadata.js` (4 assertions/product), `qa-check.js` (the whole "Structured data" section, `2459-2705`, plus whatever new JSON-LD assertions replace it), `pdp-merchandising.test.js:210-217` (2 assertions/product). Indirect: the three challenger suites' redirect-stripping middleware becomes dead code (harmless but should be deleted, since there's nothing left to strip) once the redirect is gone; `build-site-data.test.js:492-658`'s existing `generateProductJsonLd`/`generateProductBreadcrumbJsonLd` unit tests move from "testing dead code" to "testing the live path" with no changes needed to the tests themselves — a genuine win.
5. **The a11y gate would, for the first time, scan 19 real DOM trees instead of (almost certainly) re-scanning `shop.html` 19 times.** Per §1's `a11y-check.js` finding: today's "19 product-page a11y scans" are very likely not exercising distinct DOM at all. A real, non-redirecting, richer PDP (footer, cart drawer, gallery, review markup, etc. all newly present) is a **large, first-time expansion of what the zero-tolerance a11y gate actually has to pass** — 19 pages' worth of new interactive surface (galleries, any new modals) all need to individually clear `wcag2a/aa/21a/21aa/22aa/best-practice` with zero violations, on top of the existing 23 known color-contrast violations from `.dispatch-badge`/`button[data-concern="all"]` (AGENTS.md) that would now also need fixing on every genuinely-scanned PDP rather than (probably) once via `shop.html`'s re-scan.
6. **Service worker caching of product pages.** `sw.js`'s `ASSETS_TO_CACHE` precache list does not include `products/*.html` today (confirmed, `sw.js:11-54`) and `build-site-data.js`'s SW-updating pass only re-fingerprints whatever's already listed (`2827-2887`) — it doesn't add PDP URLs automatically. However, the fetch handler's network-first strategy for any HTML navigation (`sw.js:139-163`) opportunistically caches **any** same-origin page after first visit, `products/*.html` included — so no `sw.js` change is strictly required for reversal to work offline-after-first-visit, but if PDPs become the primary discovery surface, deliberately adding the 19 URLs to the precache list (trading a slightly bigger install-time payload for guaranteed offline PDP access) becomes a real product decision rather than a no-op.
7. **Netlify pretty-URL rewriting.** No `/products/<slug>` → `/products/<slug>.html` rewrite exists in `netlify.toml` today (confirmed against the full `[[redirects]]` block). If marketing/SEO wants clean URLs once PDPs are indexed, that's new `netlify.toml` (and matching `_headers`/`vercel.json`, since `build-security-headers.js` keeps all three byte-identical per `AGENTS.md` invariant 3) work, plus updating every internal link (`../shop.html`-style relative hrefs throughout the template, `search-data.js`'s `url` field, `sitemap.xml` entries) to the new shape.
8. **Header/footer path-style mismatch.** The PDP header currently uses document-relative `../assets/img/logo.png` / `../shop.html` links (subdirectory-relative), while the shared footer template's logo injection is deliberately **root-absolute** (`build-site-data.js:2132-2144`, comment: *"404.html is served at the requested URL (audit C-5), so a document-relative logo path 404s under /products/"*) — i.e. the codebase already had to solve exactly this relative-path problem once for `404.html`. Wiring the shared footer into PDPs needs the same root-absolute treatment or every footer asset link will 404 under `/products/`.
9. **Gift-card PDP is a genuine special case.** `products/yallternative-gift-card.html` already has a $10.00–$500.00 price *range* in its microdata (`itemprop="price" content="10.00"` displaying `10.00 – $500.00`) and is a digital, no-shipping product. `docs/AUDIT-2026-09-01.md:112` (DI-19) flagged its JSON-LD as previously wrong (declaring shipping/mail returns it shouldn't). Reinstating `generateProductJsonLd` for this SKU needs an explicit price-range (`AggregateOffer`, which the function already supports via `variantPriceRange`, `2895-3093`) and a shipping/return-policy override, or DI-19 recurs.
10. **`#pdpRecentlyViewedSection`/Recently-Viewed is a pre-existing gap the reversal should resolve, not just carry forward.** Per §1/§3, the feature is already fully wired in JS and fully absent from the template, and is currently inert for all real visitors regardless of the doorway decision. A reversal is the natural moment to either finish it (add the container to `renderProductPdpHtml`) or delete the dead JS/PROJECT.md contract — leaving it half-wired *and* now reachable would be a worse state than today's fully-inert one.
11. **Prefetch/speculation-rules waste.** If `assets/js/main.js`'s prefetch/speculation-rules controller (exercised by `test-challenger2-m3-m4-adversarial.browser.test.js`) is already primed to prefetch `products/*.html` hrefs on hover, today every such prefetch fetches a page whose entire purpose is to immediately redirect elsewhere — wasted bandwidth that a reversal turns into genuinely useful prefetching (not verified in depth here; flagged for follow-up, not a blocker).
