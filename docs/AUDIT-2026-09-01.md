## Deploy prerequisites before merge

None of these are code changes; all of them are needed before the branch behaves in production the way the tests say it does.

1. **Create the D1 database.** `npx wrangler d1 create yallternative-state`, paste the printed `database_id` into `workers/wrangler.toml`, and uncomment the `[[d1_databases]]` block (binding `STATE_DB`). It ships commented out on purpose: a placeholder id fails `wrangler deploy` outright, and Workers Builds runs that on every push to `main`, which would take the checkout Worker's deploys down. Optionally load the schema up front with `npx wrangler d1 execute yallternative-state --remote --file=workers/schema.sql`; `workers/state/migrations.js` applies it lazily at the first request either way.
2. **Set the Worker secrets** — never `[vars]`, never committed: `STRIPE_SECRET_KEY` (restricted key: Checkout Sessions, Coupons, Promotion Codes and Customers write, Tax Settings read — miss the Tax read and sales tax silently never switches on), `STRIPE_WEBHOOK_SECRET`, and `RESEND_API_KEY` from a Resend account with the domain verified. Optional vars: `RESTOCK_NOTIFY_EMAIL`, `GIFT_CARD_FROM_EMAIL`. `MAGIC_LINK_SECRET` is not needed — magic links are built but unwired. `STRIPE_WEBHOOK_SECRET` is load-bearing twice: it verifies Stripe's signature and it keys the gift-card code derivation, so rotate it only when no delivery is in flight.
3. **Point the Stripe webhook endpoint at the Worker** and subscribe to exactly `checkout.session.completed`, `checkout.session.expired` and `charge.refunded`. Do not also select `refund.created` — it fires for the same money. The documented endpoint is `https://yallternativeliving.com/api/stripe-webhook`, which reaches the Worker through Netlify's `/api/*` proxy; if Stripe reports signature failures, suspect that proxy first (the signature is over the exact bytes) and register the Worker directly instead: `https://yallternative-checkout.y-allternative-living.workers.dev/api/stripe-webhook`. Both spellings work — `routeOf` in `workers/checkout.js` strips a leading `/api` before matching, because the proxy's `:splat` drops the prefix and delivers `/stripe-webhook`. Delete the old Netlify endpoint only after the Worker has processed real events: `claimEvent` makes double processing impossible within one deployment, not across two.
4. **The Durable Object migration is applied by the first `wrangler deploy` from `main`.** `[[migrations]] tag = "v1"` declares `new_sqlite_classes = ["GiftCardLedger", "RateLimitCounter"]` — SQLite-backed Durable Objects, the ones included on the Workers Free plan; a class's storage backend cannot be changed after the migration is applied. Branch previews run `wrangler versions upload`, which cannot apply a migration, so **Workers Builds on branch previews may stay red until that first deploy from `main`**. A red preview build is not, on its own, evidence of a bad change. Confirm `GIFT_CARD_LEDGER`, `RATE_LIMIT_COUNTER` and `STATE_DB` appear under the Worker's bindings afterwards.
5. **Clean up Netlify.** Delete the environment variables the retired functions used (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `RESEND_API_KEY`, `RESTOCK_NOTIFY_EMAIL`, `RESTOCK_FROM_EMAIL`, `GIFT_CARD_FROM_EMAIL`, `FROM_EMAIL`). Nothing in the Netlify build reads them now, and a live Stripe key in a second provider's dashboard is a second place it can leak from. The `/api/*` proxy rule and the four `410` rules are generated by `scripts/build-security-headers.js`, so editing `netlify.toml` by hand does not survive a deploy.

**SEO decision, for the record.** Product detail pages are deliberately `noindex, follow` doorway pages that canonicalise to `shop.html` and carry **no JSON-LD**; `shop.html`'s `ItemList` carries the `Offer` data instead (`c89c861`). This is a decision, not an oversight — it is reversible, and `scripts/verify-pdp-metadata.js` is what pins it, so reversing it means changing that verifier first.

**No gift-code migration is needed.** The owner confirmed on 2026-09-01 that no gift code has ever been issued, so the ledger starts empty and there is no legacy Stripe promotion code to import. C-2 and C-3 therefore caused no loss.

## Critical

### C-1 — Unauthenticated store-credit minting

`netlify/functions/redeem-points.js:139-212`, called from `assets/js/cart.js:519-540`.

`POST /.netlify/functions/redeem-points` with `{"points":500}` creates a real Stripe coupon and promotion code worth $25 and returns the code. There is no authentication, no server-side points ledger (the only balance is `localStorage["yl_loyalty_points"]`, and nothing in the codebase ever credits it), no rate limit, and CORS reflects any `Origin` (`:140-146`). The coupon is `duration: "forever"` with no `max_redemptions` on either the coupon (`:38-48`) or the promotion code (`:68-76`), so a single minted code is also unlimited-use. The same handler is an open mail relay from `orders@yallternativeliving.com` to any address (`:186-188`), which can exhaust the Resend quota that gift-card delivery depends on.

**Fix.** Remove the endpoint until a server-side ledger keyed to an authenticated customer exists. When rebuilt: `duration: "once"`, `max_redemptions: 1`, the same `ALLOWED_ORIGINS` allowlist the sibling functions use, per-IP rate limiting, and a real email validator.

### C-2 — Gift cards applied in the cart drawer are never debited

`workers/checkout.js:1002-1065`; `netlify/functions/fulfill-gift-card.js:268-311`, `:572`.

The Worker looks up the promotion code, mints a fresh ephemeral coupon for `min(total, balance)`, and attaches that via `discounts[0][coupon]`. The original promotion code is never deactivated or reduced. The webhook's `handleGiftCardRedemption` only finds a code through `session.discounts[0].promotion_code`, which Stripe leaves `null` when a coupon was applied, so it returns before any rollover. The Worker does write `gift_card_redeemed_code` / `gift_card_promo_id` / `gift_card_amount_applied_cents` into session metadata, but nothing reads them on the completed path. Two tabs can also double-spend concurrently. The balance checker keeps reporting the full balance afterwards. The hosted-checkout path (typing the code on Stripe's page) does debit correctly, so only the site's own UI is broken. The test that covers this (`scripts/backend-functions.test.js:2077-2081`) feeds the webhook the hosted-page shape, which the Worker never produces.

Chained with C-1: mint a free voucher, buy a gift card with it (gift cards are not excluded from session discounts), receive a transferable card that C-2 makes infinite.

**Fix.** In `handleGiftCardRedemption`, read the session metadata keys first and drive the rollover from them. Better, reserve at session creation (deactivate the source promo, mint the residual) and restore on `checkout.session.expired`. Add a regression test using `discounts: [{coupon, promotion_code: null}]`. Refuse gift-card pre-application on sessions that contain `yallternative-gift-card`.

### C-3 — Service worker cross-serves gift-card balances

`sw.js:116-183`; consumers `assets/js/cart.js:499-517`, `assets/js/gift-card.js:63-100`.

The fetch handler strips the query string from the cache key and applies stale-while-revalidate to every same-origin GET that is not a navigation or `.js`/`.css`. `GET /.netlify/functions/gift-card-balance?code=…` therefore caches under a code-less key: after one valid lookup on a device, every later lookup of any code, valid or not, returns the first card's code, balance and initial amount. The drawer stores that whole object and sends its `code` to checkout, so shopper B spends shopper A's card.

**Fix.** Return early for `/.netlify/` and `/api/` before the cache-key logic; send `Cache-Control: no-store` from `gift-card-balance.js`.

### C-4 — CMS content becomes CSP-approved script

`scripts/build-site-data.js:2268-2277` (Tawk IDs into a JS string literal in a hashed inline script on 11 pages), `:1103-1126` and `:1200-1201` (JSON-LD via `JSON.stringify` without `<` escaping, so `</script>` in a product name, blurb or FAQ breaks out), `:2181-2258` (logo path, Umami and Gift Up IDs into attributes unescaped); `scripts/build-security-headers.js:119-136`.

The header generator re-hashes whatever inline scripts the freshly built HTML contains on every deploy, so injected script is automatically allowlisted. Its comment claims it verifies scripts are byte-identical across pages; it does not. All three payloads were reproduced in a scratch copy and their hashes landed in the emitted CSP. Any CMS editor, or anyone holding the CMS's GitHub token, gets script execution on the shop and checkout pages with no CSP violation.

**Fix.** Compare the computed hash set against a committed baseline and fail the build on any new hash. JSON-encode values into JS context (or move the IDs to `data-` attributes read by `main.js`); escape `<` as `<` in JSON-LD (the CMS auth worker already does this at `cms-auth/sveltia-auth.js:94-96`); route the attribute sinks through the file's own `escapeHtml`; add `pattern:` validators in `admin/config.yml`.

### C-5 — `404.html` is broken anywhere but the root

`404.html:25,42-43,67-77,108-109,256-261`.

Netlify serves `404.html` at the requested URL, and the file uses 22 document-relative paths for its CSS, six JS bundles, manifest, logo and nav links. A request for `/products/anything` renders an unstyled, scriptless page whose every escape route is another 404. The footer in the same file already uses root-absolute links. `main.js:8084` has the same bug for `translator.js`, so Google Translate never initialises on product pages.

**Fix.** Root-absolute paths in `404.html` and for the translator load.
